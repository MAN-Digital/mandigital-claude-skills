## Theme-side fix (T-1, one fix loop, done)

- **T-1** — `/tmp/cms-dryrun/build_theme.py:470`: f-string `{{% if {var}.download }}`
  renders `{% if btn.download }` — a **missing `%`**, not a spacing choice. The
  malformed tag broke HubL parsing in exactly the 5 `button_hubl()` users
  (hero, calendar_band, calendar_simple, course_detail, not_found_section).
  Fixed to `{{% if {var}.download %}}`, rebuilt, re-linted: **0 issues**.
- Red herrings killed by probe (all in `/tmp/cms-dryrun/lintprobe/`, 11 rounds):
  `elif` chains, nested `if`s, `is divisibleby`, `for/else`, `{{ module.* }}`
  inside loops, dotted conditions, SVG content, line length, file skipping —
  all pass. The linter is deterministic; earlier confusion was two probe-construction

  confirmed by re-test. No linter non-determinism remains.

## Skill bugs / gaps (dogfood output)

- **SB-1** — `scripts/validate-theme.sh:203`: gate-4 extracts URLs with
  `https?://[^\s\"'<>]+` over **raw file text**. Inside JSON, `href="URL"` is stored
  as `href=\"URL\">`, so the match swallows the escaping backslash
  (`https://www.uutilsynet.no/\`) and can never equal the allowlist entry.
  Any `https://` link inside any richtext field default fails g4 with no theme-side
  remedy. Fix: strip trailing `\` from matches, or extract from parsed JSON values.
- **SB-2 (critical)** — `scripts/validate-theme.sh:141`: gate-3 trusts the exit code
  of `hs cms lint`, but hs 8.9.1 exits **0** with `N issues found` errors. The gate
  passed 5 real syntax errors. Fix: fail on `issues found` count ≠ 0 / `✖|ERROR`
  in output (and keep exit-code check).
- **SB-3** — no lint-account story. `hs cms lint` is server-side and needs
  `source-code-read` or `content-editor-access`; the skill documents `gh` auth but
  no `hs` account/scope requirement, and `validate-theme.sh` cannot pass `--account`
  (I used an `HS_BIN` wrapper appending `--account=1969772`). Recommend: document
  required scopes + support `HS_ACCOUNT`/`--account` passthrough.
- **SB-4** — `portals.yaml` `forms:` is module→GUID (1:1); a bilingual theme needs
  per-locale forms (EN pages need EN HubSpot forms). No slot for it. Recommend:
  document the limitation or add a locale dimension.
- **SB-5 (cosmetic)** — `package-zip.sh` stamps local TZ (`date +%Y%m%d`); run at
  22:04Z produced `20260927`. Consider `date -u`.
- **SB-6 (cosmetic)** — `hs cms lint` echoes only some checked files (here 1/22
  modules + templates on the clean run). Confusing as coverage evidence; harmless.
- **SB-7** — `scripts/deploy.sh:133` vs runbook §3 step 7: the runbook says an
  unmapped form module **stops the deploy**, but deploy.sh only prints the mapped
  count. Verified: `--portal prod` with `forms: {}` (theme has 2 form modules) →
  `[DRY-RUN] 7. forms: 0 mapped form(s)`, **exit 0**. Recommend fail-closed check.
- **SB-8 (recommendation)** — no local HubL syntax precheck. A cheap tag-balance
  scan in `validate-theme.sh` (every `{%` closed by `%}` before the next tag)
  would have caught T-1 instantly without server round-trips. 11 probe rounds were
  needed because the only signal was server-side with a misleading message
  (`expected: endif` at `endfor` for a malformed `if` 2 KB earlier).
- **SB-9 (docs)** — no multilingual guidance. I invented and validated this rule:
  per-instance-per-locale values must be **text/textarea/richtext/choice** fields
  (the only `module_attribute`-overridable kinds used here); grouped/link/image
  content stays single-locale default + editor pass. Worth one runbook paragraph
  (this choice shapes field design: crumbs/lang-links/CTA use text hrefs —
  `theme/modules/page_header.module/fields.json`,
  `theme/modules/header.module/fields.json`).
